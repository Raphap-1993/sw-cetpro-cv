# 01.01 - Backlog de cambios de la siguiente iteracion

## Objetivo
Recibir y ordenar las proximas modificaciones del proyecto sin mezclar ese
frente con la homologacion ya cerrada en `001-004`.

## Estado
- fase activa para nuevos cambios: `Fase 1 - Analisis y requerimientos`
- iteracion: `post-homologacion base`
- estado del backlog: `abierto`
- items registrados: `1`

## Regla de uso
- Cada cambio nuevo entra primero aqui antes de tocar `specs/`, `apps/` o
  `qa/`.
- Si el cambio impacta solo comportamiento menor, igual se registra.
- Si el cambio abre una capacidad nueva o altera una existente de forma
  sensible, luego baja a Fase 4 con spec propia.
- Si un cambio no afecta deploy/runtime, no reabre Fase 7 por defecto.

## Estructura canonica de cada item
| Campo | Uso esperado |
| --- | --- |
| `CHG-SWCV-XXX` | Identificador unico del cambio |
| `Titulo` | Nombre corto y entendible |
| `Tipo` | `ajuste`, `mejora`, `bugfix`, `contenido`, `nueva-capacidad` |
| `Area` | `web-publica`, `backoffice`, `programas`, `contenido`, `media`, `leads`, `deploy`, `datos` |
| `Impacta feature base` | `001`, `002`, `003`, `004` o `nueva` |
| `Fases objetivo` | Normalmente `1 -> 4 -> 5 -> 6` |
| `Prioridad` | `alta`, `media`, `baja` |
| `Estado` | `captura`, `analisis`, `aprobado`, `en-spec`, `en-construccion`, `cerrado` |
| `Nota` | Restriccion, criterio o dependencia relevante |

## Flujo de la siguiente iteracion
1. Capturar el cambio aqui.
2. Decidir si cae sobre una feature base o si abre una nueva.
3. Si requiere definicion formal, bajar a `specs/` en Fase 4.
4. Implementar en Fase 5.
5. Validar en Fase 6.
6. Solo reabrir Fase 7 si el cambio toca release, proxy, dominio, runtime o backups.
